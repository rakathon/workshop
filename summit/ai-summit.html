Run these 4 skills after your implementation is complete — design test suites, build backend tests, generate feature files, and run Playwright specs.

● Post-Implementation 🕐 Total: ~23 minutes Scenario: Dishly Platform Forge v1.5+

Introduction

Your plan is ready and your app is built. Now let's test it.

The AIDD workshop ended at forge:promote. This guide covers the 4 Forge skills that turn your requirements and implementation into a complete test suite — from BDD scenarios all the way to running Playwright specs against your live app.

Note: Each skill checks its own prerequisites automatically. Just run them in order.

Before You Begin

Note: This guide picks up where the AIDD workshop left off. You should have already completed the full workshop flow — from competitive brief through to forge:promote — and have a working implementation running locally before starting these steps.

Step 1
Step 1
forge:spec-tests
🕐 ~5 minutes

Reads your requirements and spec artifacts and produces BDD test suites — one file per test type.

This skill reads your business.md, technical.md, API spec, storage schema, and UX strategy, then produces BDD scenario files for every achievable test type. For Dishly this means e2e, contract, integration, and UI e2e suites.

Say this

Claude Code — type this in the chat 
Can we design the tests

How the conversation flows

  1. Reads all available artifacts — business.md, technical.md, spec/api/*.yaml, spec/storage/*.md, spec/ux/ux-strategy.md.
  2. Determines achievable test types based on what specs exist. If an API spec is present, contract tests are generated. If a UX strategy exists, UI e2e scenarios are added.
  3. Writes one BDD suite file per test type to .forge/efforts/dishly-wave-1/spec/test/ (backend suites) and .forge/products/dishly/test/ (UI e2e suite).
  4. Each scenario includes a Verifies: BR-N traceability link back to the business requirement it covers.
Tip: If you only want UI tests, say "design e2e tests for dishly-wave-1" instead. The skill accepts a --type flag to scope the output.
Step 2
Step 2
forge:build-tests
🕐 ~5 minutes

Converts the BDD scenarios from forge:spec-tests into executable backend test code.

Reads the contract, integration, and e2e suite files and writes actual runnable test code in your project's language (TypeScript for Dishly). The skill auto-detects language and framework, writes the tests, and confirms they pass.

Say this

Claude Code — type this in the chat 
Can we implement the tests

How the conversation flows

  1. Reads BDD suite files from spec/test/ — e2e, contract, and integration suites.
  2. Auto-detects language (TypeScript/Node.js for Dishly) and writes executable test files.
  3. Runs the generated tests against the local app and confirms they pass.
  4. Reports pass/fail per scenario with traceability back to BR-N requirements.
Tip: For Dishly (React SPA, no backend API) focus on the e2e type. Contract and integration tests are more relevant for Go/Java backend services.
Step 3
Step 3
forge:spec-ui-e2e
🕐 ~3 minutes

Converts the ui-e2e-test-suite.md into Gherkin .feature files — one per UI surface — ready for Playwright.

Bridges the gap between the BDD test spec and Playwright. Validates for duplicate scenarios and missing screen coverage before writing, ensuring clean feature files before test generation begins.

Say this

Claude Code — type this in the chat 
Convert the UI test suite into Gherkin feature files, one per screen.

How the conversation flows

  1. Reads ui-e2e-test-suite.md and extracts all SC-N scenarios.
  2. Validates for duplicates, merge candidates, and missing screen coverage against ux-strategy.md.
  3. Proposes the file list — one .feature file per UI surface — and waits for your confirmation before writing.
  4. Writes files to features/us/<surface-name>/ with @SC-N traceability tags on each scenario.
Gotcha: If Forge detects duplicate scenarios it will ask you to confirm removal before writing. Reply "yes, remove duplicates" to proceed.
Step 4
Step 4
forge:build-playwright-tests
🕐 ~10 minutes

Takes the Gherkin .feature files, navigates your live app via browser to discover real selectors, generates Playwright .spec.ts files, runs them, and auto-fixes failures.

Full UI test lifecycle in one command. Forge uses a live browser via Playwright MCP to discover real CSS selectors from the DOM — no guessing. It generates the spec files, runs them, auto-fixes any failing selectors (up to 3 cycles), and validates the output.

Say this

Claude Code — type this in the chat 
The feature files are ready. Generate Playwright specs, run them against the local app, and fix any failures.

How the conversation flows

  1. Verifies Playwright MCP is running — auto-installs if missing. Navigates to your local app to confirm it's live.
  2. Reads each .feature file and walks through every step using a live browser — querying the DOM to find real CSS selectors.
  3. Generates .spec.ts files with real selectors, environment guards, and user-type checks.
  4. Runs the specs. If any fail, re-queries the DOM and fixes selectors — up to 3 auto-fix cycles.
  5. Validates the final specs and prints a summary report of passed/failed/skipped.
Gotcha: Make sure your app is running on http://localhost:5173 before running this skill. Forge needs a live browser to discover selectors.
Tip: If Playwright MCP is not installed, Forge will auto-install it and ask you to restart Claude Code. Just restart and re-run — it picks up where it left off.
